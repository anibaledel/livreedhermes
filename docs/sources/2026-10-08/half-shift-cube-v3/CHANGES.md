## Version 3 — all twelve files, in the layout the scripts expect

**What version 2 got wrong.** Version 2 contained three files only:
`cube_edges.py`, `cube_edges.log` and `CHANGES.md`. Its note was written as a
patch — *"replace `cube_edges.py` by the file in this folder"* — which assumes
the files of version 1 are present. **A Zenodo version does not inherit from
the previous one:** each version is the complete set of files of the record.
Anyone resolving the all-versions DOI therefore obtained a single script that
imports absent modules, with no reference data to read. Version 1 holds the
full set, but with the `cube_edges.py` that version 2 was correcting, so
neither version stands on its own.

**What version 3 contains.** The eight scripts and the three reference files
named in the record description, plus the output of every script.

```
tools/   croisements.py  croix_ansee.py  cube_croisements.py  cube_edges.py
         make_figures.py  paires_croisees.py  selection_ordre6.py
         verif_carre_magique.py
data/    fonds_ecran_v1.json  referent_256_v3.json  referent_360_v3.json
logs/    one .log per script, the output of the run recorded below
fig/     the five figures of the paper, as regenerated by make_figures.py
```

**Keep the layout when you extract.** `cube_edges.py` resolves its data with

```python
REPO_ROOT = os.path.dirname(os.path.dirname(os.path.abspath(__file__)))
DATA = os.path.join(REPO_ROOT, 'data', 'referent_360_v3.json')
```

that is, a `data/` directory beside the directory holding the script. Flattening
the archive into a single folder makes it look one level too high and fail with
*"données introuvables"*. Run the scripts from `tools/`.

`SHA256SUMS.txt` lists every file of this archive except itself. Check it

`paires_croisees.py` end with their own elapsed time, which depends on the
machine. Everything above that line is deterministic and must match.

# Version 2 of doi:10.5281/zenodo.22862111 — what changes

Replace `cube_edges.py` by the file in this folder (the current
`tools/cube_edges.py` of github.com/anibaledel/livreedhermes, commit df20c9e,
24 Sept. 2026) and add `cube_edges.log`, its output.

Reason: the script deposited in version 1 carries an obsolete docstring —
"384 triplets, 256 grilles, 128 pavages, trois familles" — and reads
`data/fonds_ecran_v1.json`, the old 48-layer file. The paper (Theorem 3) and
the current script say **512 triplets, 256 grids, 128 tilings, four
families**, those containing the base yang. The four-family count is the
right one: it is computed on the 60 layers of `referent_360_v3.json`; the
48-layer file lacked the single-base family {yang}, which has 128 admissible
triplets and adds no new grid (Lemma 2), hence 256 grids and 128 tilings in
both counts. The current script reads `referent_360_v3.json` (already in the
deposit) and uses `fonds_ecran_v1.json` only as a control.

Verified 26 Sept. 2026: `python3 tools/cube_edges.py` → 512/1024 triplets,
256 grids, 128 tilings, 4 families (BASE-YANG, PAR2-YANG-YIN-MUT,
PAR2-YIN-YANG, PAR3-SANS-YANG-MUT), 43 s.
