Démonstration : message ANIBALAMIOTX

ANIBALAMIOTX est d'abord chiffré avec AES-256-GCM (clé stéganographique de 256 bits), puis le texte chiffré est dissimulé dans une grille 60×60 de nombres aléatoires, aux positions désignées par la taille de bloc (Clé B), l'orientation (Clé C) et la forme du Référent 256 (Clé 2) — le reste est du bruit indiscernable. La confidentialité vient du chiffrement, pas de la géométrie.

Échange de clés — X25519 authentifié (triple DH)

Deux correspondants dérivent la même session sans transmettre de secret. Trois Diffie-Hellman entrent dans la dérivation : éphémère × éphémère pour la forward secrecy, puis éphémère × identité de chaque côté, ce qui lie les identités long terme à la session. Un relais qui substitue ses propres clés éphémères ne possède aucune des deux identités privées : il ne peut pas calculer la clé. Même protocole que la CLI Python — une session dérivée ici et une session dérivée par secu-box exchange aboutissent à la même clé.

Ce qui vous protège : la vérification, par un canal séparé (appel vocal, rencontre), du fingerprint d'identité que l'offer de votre correspondant annonce. Sans elle, rien ne distingue votre correspondant d'un relais qui se présenterait avec sa propre identité. La chaîne d'authentification affichée après dérivation reste disponible en secours, si le fingerprint n'a pas pu être confronté avant.

Sur votre identité : sa clé privée est conservée dans ce navigateur sous une forme que le code de la page ne peut pas lire — il peut seulement s'en servir pour dériver. Contrepartie : elle ne peut être ni sauvegardée ni déplacée vers un autre navigateur. Effacer les données du site la détruit définitivement, avec le fingerprint que vos correspondants connaissent. Une identité de la CLI Python ne peut pas non plus être importée ici : chaque côté garde la sienne, ce qui n'empêche pas les deux de dialoguer.

Grille Carter 90×90 (grammaire dérivée de la clé)

Une seule passphrase dérive le rôle (pur / structuré / message), la forme et l'orientation de chacun des 225 blocs 6×6 — aucun placement n'est stocké en dehors de la clé. Les blocs « structurés » et « message » sont statistiquement indiscernables sans elle. Chaque encodage tire un sel aléatoire, affiché après coup : le transmettre avec la passphrase. Il n'est pas secret et ne figure pas dans le CSV, mais sans lui la grille reste close — et c'est lui qui empêche qu'une table précalculée sur des passphrases courantes n'ouvre les grilles de tous les utilisateurs à la fois.

Stéganographie géométrique — chiffrer puis dissimuler

Ce système est une application cryptographique des constructions arithmogéométriques développées dans La Livrée d'Hermès (Anibal Edelberto Amiot, 2026). Soumis à l'IACR Cryptology ePrint Archive en septembre 2026. Architecture revue suite à un audit cryptologique externe (2026-09-10).

Principe : le message est d'abord chiffré (AES-256-GCM), puis le texte chiffré est dissimulé dans une grille de nombres aléatoires. La confidentialité vient du chiffrement, la géométrie ne fait que cacher où se trouve le texte chiffré. Sans les clés, la grille est statistiquement indiscernable du bruit aléatoire.

Clé stéganographique — chiffrement : clé AES-256-GCM de 256 bits, générée aléatoirement par message. Chiffre le message avant toute dissimulation ; authentifie le déchiffrement (une clé ou des données incorrectes sont détectées, pas silencieusement corrompues).

Clé B — grammaire des blocs : taille de cellule par bloc — 6×6, 12×12, 18×18 ou 30×30.

Clé C — orientations : l'une des 8 transformations diédrales (D4 : rotations et miroirs) appliquée à chaque sous-bloc 6×6.

Clé 2 — formes et couleurs : sélection d'une forme et d'une couleur (bleu/orange) dans le Référent 256, par bloc.

Ancienne Clé A retirée : l'audit a constaté que le mélange secret du référent (Clé A) était entièrement redondant avec la Clé 2 — 0 bit de sécurité apporté malgré un espace de clés apparent de 2^1684. Le Référent 256 est maintenant utilisé directement.

Espace de clés (honnête) : confidentialité = 256 bits (AES-256-GCM) ; dissimulation géométrique = Clé B + Clé C + Clé 2 (jusqu'à 2^2300 bits pour une grille 60×60 en blocs 12×12). Une clé de dissimulation incorrecte échoue désormais à l'authentification AES-GCM — une erreur explicite, plus une fausse lecture plausible comme dans les versions antérieures.
Kerckhoffs : le système respecte le principe de Kerckhoffs (1883) — l'algorithme est entièrement public, le secret repose uniquement sur les clés et, optionnellement, sur des référents personnalisés.

Brevet antécédent : FR2865054 (2004) — composition automatisée d'un motif symbolique à partir d'une relation mathématique.

Architecture SecuBox

SecuBox assemble cinq composants indépendants, chacun documenté et vérifié séparément dans ses propres onglets :

1. Exchange (X25519) — échange de clés authentifié par triple Diffie-Hellman sur courbe Curve25519 (natif dans l'API Web Crypto de ce navigateur) : éphémère × éphémère pour la forward secrecy, puis éphémère × identité de chaque côté, ce qui lie les identités long terme à la session. HKDF-SHA256 sur le transcript complet — les quatre clés publiques — dérive la clé de session. Un relais qui substitue ses clés éphémères ne possède aucune des deux identités privées et ne peut donc pas calculer la clé ; l'authentification tient à la vérification hors bande du fingerprint d'identité annoncé par l'offer. La clé privée éphémère est détruite après dérivation. Même protocole que la CLI Python : une session dérivée ici et une session dérivée par secu-box exchange aboutissent à la même clé — vérifié par dérivation croisée des deux implémentations. Seule l'identité elle-même n'est pas transportable d'un côté à l'autre : la CLI protège la sienne par Argon2id, absent de Web Crypto, et celle du navigateur est non extractible par construction. Chaque côté garde donc la sienne.

2. Message / Déchiffrer — stéganographie géométrique (voir ci-dessus), utilisant les clés dérivées par la session Exchange active.

3. Vault — chiffrement de fichiers en local, AES-256-GCM par entrée, manifest chiffré, HMAC-SHA256 global (architecture inspirée de vault_lib.py).

4. Chiffrement fichier — SPN géométrique (Ref256+Ref360) en couche de diversification de clé, AES-256-GCM en couche de chiffrement authentifié (voir l'onglet Chiffrement).

5. Référents 256 et 360 — les tables de formes géométriques (croix ansée, Jacquard) qui alimentent les quatre composants ci-dessus.

Note sur les substitutions de chiffrement : la référence Python (secu_box.py, vault_lib.py, disk_lib.py) utilise XChaCha20-Poly1305, absent de l'API Web Crypto des navigateurs. AES-256-GCM lui est substitué dans cette page — même classe de garantie (AEAD, 256 bits, standard audité) via l'implémentation native du navigateur plutôt qu'une implémentation ChaCha20 maison. X25519 est en revanche implémenté nativement et identiquement des deux côtés.

Écart connu — dérivation de clé du Vault : depuis sa version 1.2, vault_lib.py utilise Argon2id (memory-hard, résistant GPU/ASIC) au lieu de PBKDF2 pour sa dérivation de clé interne. Les navigateurs n'ont ni Argon2id ni scrypt en natif — contrairement aux cas ci-dessus, il n'existe pas d'équivalent Web Crypto à substituer sans ajouter une dépendance externe. Le Vault de cette page reste donc sur PBKDF2 (300 000 itérations) et, de ce fait, moins résistant au brute-force par GPU/ASIC que son homologue Python. Pour une utilisation sensible en production, préférer la CLI Python (secu-box vault).

Avertissement général : SecuBox est un système expérimental basé sur des constructions géométriques originales. La couche cryptographique (AES-256-GCM, X25519, HKDF, PBKDF2) est standard et auditée. La couche géométrique (La Livrée d'Hermès) est en cours d'évaluation formelle — voir l'audit cryptologique externe du 2026-09-10 mentionné dans les onglets Chiffrement et Déchiffrer.

Chiffrement hybride — géométrique + AES-256-GCM

Architecture à deux couches, suite à un audit cryptologique externe : une couche géométrique (SPN Ref256+Ref360, S-box GF(2⁸), 4 tours) dérive une clé de session unique par secteur — diversification de clé, pas le chiffrement lui-même — puis AES-256-GCM chiffre et authentifie chaque secteur individuellement, avec une authentification HMAC-SHA256 globale par-dessus. Une passphrase incorrecte ou un fichier altéré sont détectés, jamais rendus en bruit silencieux. Distinct de l'outil de stéganographie ci-dessus. Entièrement côté client : la passphrase et les fichiers ne quittent jamais le navigateur.

Statistiques de sécurité

Couche géométrique (diversification de clé) : SPN Ref256+Ref360 — S-box GF(2⁸) (max_DDT ≤ 4 prouvé, Nyberg 1994), permutation Ref256 (12 288 configurations), MixBlock MDS (ShiftRows+MixColumns AES, branch number ≥4), permutation Ref360 (342 configurations), 4 tours — dérive une clé de session de 256 bits par secteur, non revendiquée comme chiffrement autonome
Couche standard (confidentialité + intégrité) : AES-256-GCM par secteur, tag d'authentification de 128 bits — la référence Python utilise XChaCha20-Poly1305 (absent de l'API Web Crypto des navigateurs) ; AES-256-GCM lui est substitué ici, même classe de garantie via l'implémentation native et auditée du navigateur
Dérivation de clé : PBKDF2-SHA256, 300 000 itérations — une fois passphrase → clé maître (sel de 128 bits géré par la page), une seconde fois clé maître → clé géométrique (sel de 256 bits propre à chaque fichier)
Nonce : 192 bits (aléatoire par fichier), un nonce distinct par secteur dérivé via HKDF-SHA256
Intégrité : tag AES-GCM par secteur + HMAC-SHA256 global (256 bits) — détecte toute altération ou passphrase incorrecte, jamais rendue en bruit silencieux
