การสาธิต: ข้อความ ANIBALAMIOTX

ANIBALAMIOTX ถูกเข้ารหัสด้วย XChaCha20-Poly1305 ก่อน (คีย์หลักขนาด 256 บิต) จากนั้นข้อความที่เข้ารหัสแล้วจะถูกกระจายลงบนบล็อกที่คีย์เดียวกันนั้นกำหนดให้เป็น “ข้อความ” ในตาราง 90×90 — ส่วนที่เหลือเป็นสัญญาณรบกวนที่แยกไม่ออก รวมถึงบล็อก “มีโครงสร้าง” ซึ่งหากไม่มีคีย์ก็เหมือนกับบล็อก “ข้อความ” ในเชิงสถิติ ความลับมาจากการเข้ารหัส ส่วนเรขาคณิตทำหน้าที่เพียงซ่อนตำแหน่งของข้อความที่เข้ารหัสแล้ว

การแลกเปลี่ยนคีย์ — X25519 แบบยืนยันตัวตน (triple DH)

คู่สื่อสารสองฝ่ายได้เซสชันเดียวกันโดยไม่ต้องส่งความลับใด ๆ การสร้างคีย์ใช้ Diffie-Hellman สามชุด: ชั่วคราว × ชั่วคราว เพื่อ forward secrecy จากนั้น ชั่วคราว × ตัวตน ของแต่ละฝ่าย ซึ่งผูกตัวตนระยะยาวเข้ากับเซสชัน ตัวกลางที่สอดแทรกคีย์ชั่วคราวของตนเองเข้ามาไม่มีคีย์ส่วนตัวของตัวตนฝ่ายใดเลย จึงคำนวณคีย์ไม่ได้ ใช้โปรโตคอลเดียวกับ CLI Python — เซสชันที่สร้างที่นี่และเซสชันที่สร้างด้วย secu-box exchange จะได้คีย์เดียวกัน

สิ่งที่ปกป้องคุณ: การตรวจสอบ fingerprint ของตัวตนที่ offer ของคู่สื่อสารประกาศไว้ ผ่านช่องทางแยกต่างหาก (โทรศัพท์ หรือพบกันตัวจริง) หากไม่ตรวจสอบ ก็ไม่มีสิ่งใดแยกคู่สื่อสารของคุณออกจากตัวกลางที่แสดงตัวด้วยตัวตนของตนเองได้ สายการยืนยันตัวตนที่แสดงหลังการสร้างเซสชันยังใช้เป็นทางสำรองได้ หากยังไม่ได้เทียบ fingerprint ไว้ก่อน

เกี่ยวกับตัวตนของคุณ: คีย์ส่วนตัวถูกเก็บในเบราว์เซอร์นี้ในรูปแบบที่โค้ดของหน้าเว็บอ่านไม่ได้ — ทำได้เพียงใช้คีย์นั้นเพื่อสร้างเซสชัน ข้อแลกเปลี่ยนคือ ไม่สามารถสำรองหรือย้ายคีย์ไปยังเบราว์เซอร์อื่นได้ การล้างข้อมูลของเว็บไซต์จะทำลายคีย์อย่างถาวร พร้อมกับ fingerprint ที่คู่สื่อสารของคุณรู้จัก ตัวตนจาก CLI Python ก็นำเข้าที่นี่ไม่ได้เช่นกัน: แต่ละฝ่ายเก็บตัวตนของตนไว้ ซึ่งไม่ได้ขัดขวางให้ทั้งสองฝ่ายสื่อสารกัน

คำเตือน: ไฟล์ของคุณถูกเข้ารหัสภายในเครื่อง โปรดเก็บ passphrase ไว้ให้ดี — หากไม่มี passphrase ไฟล์จะกู้คืนไม่ได้ การสร้างคีย์: PBKDF2-SHA256 (300 000 รอบ) ทนต่อการเดาแบบ brute-force ด้วย GPU/ASIC ได้น้อยกว่า Argon2id ของ CLI Python — สำหรับการใช้งานที่อ่อนไหวในระบบจริง ควรใช้ secu-box vault (ดูแท็บ เกี่ยวกับ)

ตัวอ้างอิง 256 — ตารางรูปทรงของกางเขนหูหิ้ว

รูปแบบเรขาคณิตที่แตกต่างกัน 256 แบบ: ไม่ใช่การหมุน แต่เป็นการระบายสีทั้งหมดที่เป็นไปตามเกณฑ์ I ถึง IV ของกางเขนหูหิ้ว (นับครบทุกกรณี 128 แบบต่อไครัลลิตี EGO/ALTER — ดูบทความ The Ansate Cross) วางเมาส์เหนือช่องเพื่อดูตำแหน่ง ×2 สี = 512 รูปทรงที่ใช้ได้

ตัวอ้างอิง 360 — แผ่นลายฌักการ์

60 ภาพ × 6 ระดับ = 360 แผ่นลาย (15 ตระกูล × 4 ลักษณะ) แต่ละแผ่นลายเลือกตำแหน่งอ่าน 8 ตำแหน่งในบล็อก 12×12 (— รูปทรงที่สกัดจากไฟล์ SVG ต้นฉบับ)

การซ่อนข้อมูลเชิงเรขาคณิต — เข้ารหัสก่อนแล้วจึงซ่อน

ระบบนี้เป็นการประยุกต์ด้านวิทยาการเข้ารหัสของโครงสร้างเลขาคณิตศาสตร์ที่พัฒนาไว้ใน La Livrée d'Hermès (Anibal Edelberto Amiot, 2026) ส่งไปยัง IACR Cryptology ePrint Archive ในเดือนกันยายน 2026 สถาปัตยกรรมได้รับการทบทวนหลังการตรวจสอบด้านวิทยาการเข้ารหัสจากภายนอก (2026-09-10)

หลักการ: ข้อความถูกเข้ารหัสก่อน (XChaCha20-Poly1305) จากนั้นข้อความที่เข้ารหัสแล้วจะถูกกระจายลงบนบล็อกของตารางตัวเลข — ส่วนที่เหลือเป็นสัญญาณรบกวนแบบสม่ำเสมอ ความลับมาจากการเข้ารหัส ส่วนเรขาคณิตทำหน้าที่เพียงซ่อนตำแหน่งของข้อความที่เข้ารหัสแล้ว หากไม่มีคีย์ ตารางจะแยกไม่ออกจากสัญญาณรบกวนแบบสุ่มในเชิงสถิติ: ค่า χ² ที่แสดงในแท็บ เดโม คือการตรวจสอบเรื่องนี้ ไม่ใช่เพียงคำกล่าวอ้าง

คีย์หลัก: 256 บิต สร้างแบบสุ่ม (หรือได้จาก passphrase หรือจากเซสชัน Exchange) คีย์เดียวถูกแยกด้วย HKDF-SHA256 เป็นคีย์เข้ารหัสและคีย์ไวยากรณ์ — การใช้งานทั้งสองนี้ไม่เคยใช้วัสดุคีย์เดียวกัน

ไวยากรณ์: คีย์ไวยากรณ์กำหนดบทบาท (บริสุทธิ์ / มีโครงสร้าง / ข้อความ) และรูปทรงให้แต่ละบล็อกของตาราง โดยสุ่มเลือกจากตัวอ้างอิง 256 (กางเขนหูหิ้ว) หรือจากตัวอ้างอิง 6×6 ที่สร้างใหม่สำหรับ Carter-Random บล็อก “มีโครงสร้าง” และ “ข้อความ” แยกจากกันไม่ออกในเชิงสถิติหากไม่มีคีย์ — บล็อกเหล่านี้มีอยู่เพื่อเหตุผลนี้โดยเฉพาะ ไม่ได้มีไว้บรรจุเนื้อหา

การยืนยันความถูกต้อง: คีย์หรือข้อมูลที่ไม่ถูกต้องจะล้มเหลวในการยืนยันความถูกต้องอย่างชัดแจ้ง (Poly1305) ไม่มีวันถูกแสดงผลเป็นการอ่านที่ผิดแต่ดูน่าเชื่อ

รูปแบบ: Carter-256 (ตัวอ้างอิงกางเขนหูหิ้วแบบคงที่) และ Carter-Random (ตัวอ้างอิง 6×6 ที่สร้างใหม่ตามคีย์) ถูกพอร์ตและตรวจสอบใน JavaScript เทียบกับเวกเตอร์ที่สร้างโดยโค้ด Python รูปแบบอื่นของระบบเดียวกัน (Deniable, Carter-360, Carter-Mix, Carter-18, Carter-Hybrid) มีอยู่ในฝั่ง Python แต่ยังไม่ได้พอร์ตมายังเบราว์เซอร์
Kerckhoffs: ระบบนี้เป็นไปตามหลักการของ Kerckhoffs (1883) — อัลกอริทึมเปิดเผยต่อสาธารณะทั้งหมด ความลับขึ้นอยู่กับคีย์เท่านั้น และอาจรวมถึงตัวอ้างอิงที่ปรับแต่งเองด้วย

สิทธิบัตรก่อนหน้า: FR2865054 (2004) — การประกอบลวดลายเชิงสัญลักษณ์โดยอัตโนมัติจากความสัมพันธ์ทางคณิตศาสตร์

สถาปัตยกรรม SecuBox

SecuBox ประกอบด้วยองค์ประกอบอิสระห้าส่วน แต่ละส่วนมีเอกสารและได้รับการตรวจสอบแยกกันในแท็บของตนเอง:

1. Exchange (X25519) — การแลกเปลี่ยนคีย์แบบยืนยันตัวตนด้วย triple Diffie-Hellman บนเส้นโค้ง Curve25519 (มีมาในตัวใน API Web Crypto ของเบราว์เซอร์นี้): ชั่วคราว × ชั่วคราว เพื่อ forward secrecy จากนั้น ชั่วคราว × ตัวตน ของแต่ละฝ่าย ซึ่งผูกตัวตนระยะยาวเข้ากับเซสชัน HKDF-SHA256 บน transcript ทั้งหมด — คีย์สาธารณะทั้งสี่ — สร้างคีย์เซสชัน ตัวกลางที่สอดแทรกคีย์ชั่วคราวของตนเองไม่มีคีย์ส่วนตัวของตัวตนฝ่ายใดเลย จึงคำนวณคีย์ไม่ได้ การยืนยันตัวตนขึ้นอยู่กับการตรวจสอบ fingerprint ของตัวตนที่ offer ประกาศไว้ผ่านช่องทางอื่น คีย์ส่วนตัวชั่วคราวถูกทำลายหลังการสร้างเซสชัน ใช้โปรโตคอลเดียวกับ CLI Python: เซสชันที่สร้างที่นี่และเซสชันที่สร้างด้วย secu-box exchange จะได้คีย์เดียวกัน — ตรวจสอบแล้วด้วยการสร้างเซสชันไขว้ระหว่างสองการใช้งาน มีเพียงตัวตนเท่านั้นที่ย้ายข้ามฝั่งไม่ได้: CLI ปกป้องตัวตนของตนด้วย Argon2id ซึ่งไม่มีใน Web Crypto และตัวตนของเบราว์เซอร์ถูกออกแบบให้ดึงออกไม่ได้ แต่ละฝั่งจึงเก็บตัวตนของตนไว้

2. ข้อความ / ถอดรหัส — การซ่อนข้อมูลเชิงเรขาคณิต Carter (ดูด้านบน) โดยใช้คีย์หลักที่ได้จากเซสชัน Exchange ที่ใช้งานอยู่ จาก passphrase หรือป้อนโดยตรง

3. Vault — การเข้ารหัสไฟล์ภายในเครื่อง AES-256-GCM ต่อรายการ, manifest ที่เข้ารหัส, HMAC-SHA256 ทั้งชุด (สถาปัตยกรรมได้แรงบันดาลใจจาก vault_lib.py)

4. การเข้ารหัสไฟล์ — SPN เชิงเรขาคณิต (Ref256+Ref360) เป็นชั้นกระจายคีย์ และ AES-256-GCM เป็นชั้นการเข้ารหัสแบบยืนยันความถูกต้อง (ดูแท็บ การเข้ารหัส)

5. ตัวอ้างอิง 256 และ 360 — ตารางรูปทรงเรขาคณิต (กางเขนหูหิ้ว, ฌักการ์) ที่ป้อนข้อมูลให้องค์ประกอบข้างต้น

หมายเหตุเรื่องการทดแทนอัลกอริทึมเข้ารหัส: องค์ประกอบ ข้อความ/ถอดรหัส (2) ใช้ XChaCha20-Poly1305 ใน JavaScript ล้วน เหมือนกับต้นแบบ Python (stegano/carter.py, stegano/carter_random.py) และตรวจสอบเทียบกับเวกเตอร์ของต้นแบบแล้ว — ส่วนนี้ไม่มีการทดแทนอีกต่อไป Vault (3) และการเข้ารหัสไฟล์ (4) ยังคงใช้ AES-256-GCM ที่มีในตัวเบราว์เซอร์ เนื่องจาก API Web Crypto ไม่มี XChaCha20-Poly1305 ให้สององค์ประกอบนี้ใช้ ระดับการรับประกันเดียวกัน (AEAD, 256 บิต, มาตรฐานที่ผ่านการตรวจสอบ) X25519 ถูกใช้งานแบบมีในตัวและเหมือนกันทั้งสองฝั่ง

ความต่างที่ทราบอยู่แล้ว — การสร้างคีย์ของ Vault: ตั้งแต่เวอร์ชัน 1.2 vault_lib.py ใช้ Argon2id (memory-hard ทนต่อ GPU/ASIC) แทน PBKDF2 สำหรับการสร้างคีย์ภายใน เบราว์เซอร์ไม่มีทั้ง Argon2id และ scrypt ในตัว — ต่างจากกรณีข้างต้น ไม่มีสิ่งเทียบเท่าใน Web Crypto ที่จะนำมาทดแทนได้โดยไม่เพิ่มการพึ่งพาภายนอก Vault ของหน้านี้จึงยังคงใช้ PBKDF2 (300 000 รอบ) และด้วยเหตุนี้จึงทนต่อ brute-force ด้วย GPU/ASIC ได้น้อยกว่าฝั่ง Python สำหรับการใช้งานที่อ่อนไหวในระบบจริง ควรใช้ CLI Python (secu-box vault)

คำเตือนทั่วไป: SecuBox เป็นระบบทดลองที่ตั้งอยู่บนโครงสร้างเรขาคณิตที่คิดขึ้นใหม่ ชั้นวิทยาการเข้ารหัส (AES-256-GCM, X25519, HKDF, PBKDF2) เป็นมาตรฐานและผ่านการตรวจสอบแล้ว ชั้นเรขาคณิต (La Livrée d'Hermès) อยู่ระหว่างการประเมินอย่างเป็นทางการ — ดูการตรวจสอบด้านวิทยาการเข้ารหัสจากภายนอกวันที่ 2026-09-10 ที่กล่าวถึงในแท็บ การเข้ารหัส และ ถอดรหัส

การเข้ารหัสแบบผสม — เชิงเรขาคณิต + AES-256-GCM

สถาปัตยกรรมสองชั้น ซึ่งปรับตามการตรวจสอบด้านวิทยาการเข้ารหัสจากภายนอก: ชั้นเรขาคณิต (SPN Ref256+Ref360, S-box GF(2⁸), 4 รอบ) สร้างคีย์เซสชันเฉพาะสำหรับแต่ละเซกเตอร์ — เป็นการกระจายคีย์ ไม่ใช่ตัวการเข้ารหัสเอง — จากนั้น AES-256-GCM เข้ารหัสและยืนยันความถูกต้องของแต่ละเซกเตอร์แยกกัน โดยมีการยืนยันความถูกต้อง HMAC-SHA256 ทั้งชุดซ้อนอยู่ด้านบน passphrase ที่ไม่ถูกต้องหรือไฟล์ที่ถูกแก้ไขจะถูกตรวจพบ ไม่มีวันกลายเป็นสัญญาณรบกวนแบบเงียบ ๆ แยกต่างหากจากเครื่องมือซ่อนข้อมูลด้านบน ทำงานฝั่งไคลเอนต์ทั้งหมด: passphrase และไฟล์ไม่เคยออกจากเบราว์เซอร์

ป้อนเพียงครั้งเดียว ใช้โดยตรงกับปุ่ม เข้ารหัส และ ถอดรหัส ด้านล่าง

เข้ารหัสไฟล์

ถอดรหัสไฟล์

passphrase ที่ไม่ถูกต้องหรือไฟล์ที่ถูกแก้ไขจะทำให้เกิดข้อผิดพลาดอย่างชัดแจ้ง (การตรวจสอบ HMAC-SHA256) แทนที่จะให้ผลเป็นสัญญาณรบกวนแบบเงียบ ๆ

สถิติด้านความปลอดภัย

ชั้นเรขาคณิต (การกระจายคีย์): SPN Ref256+Ref360 — S-box GF(2⁸) (max_DDT ≤ 4 พิสูจน์แล้ว, Nyberg 1994), การเรียงสับเปลี่ยน Ref256 (12 288 รูปแบบ), MixBlock MDS (ShiftRows+MixColumns AES, branch number ≥4), การเรียงสับเปลี่ยน Ref360 (342 รูปแบบ), 4 รอบ — สร้างคีย์เซสชันขนาด 256 บิตต่อเซกเตอร์ ไม่ได้อ้างว่าเป็นการเข้ารหัสที่ใช้ได้ด้วยตัวเอง
ชั้นมาตรฐาน (ความลับ + ความครบถ้วน): AES-256-GCM ต่อเซกเตอร์, tag ยืนยันความถูกต้องขนาด 128 บิต — ต้นแบบ Python ใช้ XChaCha20-Poly1305 (ไม่มีใน API Web Crypto ของเบราว์เซอร์) ที่นี่จึงใช้ AES-256-GCM แทน ระดับการรับประกันเดียวกันผ่านการใช้งานที่มีในตัวและผ่านการตรวจสอบของเบราว์เซอร์
การสร้างคีย์: PBKDF2-SHA256, 300 000 รอบ — ครั้งแรก passphrase → คีย์หลัก (ซอลต์ 128 บิตที่หน้าเว็บจัดการ) ครั้งที่สอง คีย์หลัก → คีย์เรขาคณิต (ซอลต์ 256 บิตเฉพาะของแต่ละไฟล์)
Nonce: 192 บิต (สุ่มต่อไฟล์) โดยมี nonce แยกกันต่อเซกเตอร์ที่ได้ผ่าน HKDF-SHA256
ความครบถ้วน: tag AES-GCM ต่อเซกเตอร์ + HMAC-SHA256 ทั้งชุด (256 บิต) — ตรวจพบการแก้ไขใด ๆ หรือ passphrase ที่ไม่ถูกต้อง ไม่มีวันกลายเป็นสัญญาณรบกวนแบบเงียบ ๆ
